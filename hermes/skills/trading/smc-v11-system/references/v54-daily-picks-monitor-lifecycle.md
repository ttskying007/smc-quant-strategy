# V54 Daily Picks Monitor Lifecycle

Related: `references/daily-ops-observability.md` defines the anti-盲盒 logging layer for daily selector status, pick funnel rejection reasons, realtime trigger causes, review/autopsy attribution, analysis freshness, `/logs`, and `/api/logs`.

## When to use
Use this reference when extending the SMC dashboard from static backtest picks into an operational daily watchlist / real-time monitor workflow.

## Durable architecture pattern
Do not treat `vNN_picks.json` as the live monitor itself. Keep a separate monitor lifecycle store:

- Backtest/engine output: `/root/.hermes/smc_opt_vNN/vNN_picks.json`
- Daily/manual monitor state: `/root/.hermes/smc_monitor/positions.json`
- Buy/sell operation ledger: `/root/.hermes/smc_monitor/trade_ledger.json` (append-only UI audit trail from activation date; highlight same-day operations)
- Daily import snapshots: `/root/.hermes/smc_monitor/daily/YYYYMMDD_auto_daily.json`
- Closed-position reviews: `/root/.hermes/smc_monitor/closed_reviews.json`

This separation prevents historical trades/picks from being mistaken for active candidates and preserves auditability after TP/SL triggers.

## Pick lifecycle states
Recommended monitor states:

1. `OPEN` — active watch/position, created from auto daily pick or manual pick.
2. `CLOSED` — TP/SL triggered or manually closed.
3. `REVIEWED` — closed item has a post-exit diagnosis and repair proposal.

Each monitor row should carry enough original provenance to replay:

- `symbol`
- `source`: `auto_daily` or `manual`
- `pick_date`
- `category`
- `entry_price`, `sl_price`, `tp1_price`
- `zone_type`, `conf_type`, `entry_type`, `seq`
- `zone_idx`, `conf_index`
- `raw_pick` when generated by engine

## V66 full closed-loop automation

For complete production automation (selector → daily pick audit → auto-ingest → live SL/TP polling → trade ledger → closed reviews → `/logs` audit UI), see `references/v66-closed-loop-automation-audit.md`. This is the required checklist when the user asks whether the SMC system is “fully closed loop”; do not treat a generated picks file or one working page as sufficient.

## Operation ledger on `/live`

Keep a separate append-only buy/sell ledger for follow-trading and review:

- Store at `/root/.hermes/smc_monitor/trade_ledger.json`.
- Append `BUY` when a daily/manual candidate is actually imported into `positions.json`.
- Append `SELL` exactly once when `update_with_live_results()` closes an open position on `SL_HIT` or `TP_HIT`.
- A-share T+1 is a hard gate: before closing, require `date_key(closed_at_or_now) > date_key(created_at)`. Same-day `SL_HIT`/`TP_HIT` must remain open and be surfaced as `T1_LOCKED` / “T+1锁定，今日禁止卖出”, not written as SELL/review records.
- Deduplicate by `position_id + action + created_at/closed_at` so browser refreshes do not duplicate rows.
- `/api/live-prices` should include `tradeLedger` and enrich open BUY rows with current price/PnL from the live result map.
- `/live` should render this ledger below the real-time table with: action, symbol, engine, select date, buy date, sell date, score, quality, retrace, current price, zone, PnL, SL, TP, sequence, reason/source. Same-day operations get a visual highlight.

## Daily auto ingest
Daily auto pick ingest should run the engine first, then import only valid live candidates into monitor state. Cron pattern used in this session:

```cron
5 9 * * 1-5 root cd /root/.hermes/scripts/v25 && /usr/bin/python3 v54_engine.py >> /root/.hermes/smc_monitor/cron.log 2>&1 && /usr/bin/python3 v54_daily_pick_ingest.py >> /root/.hermes/smc_monitor/cron.log 2>&1
```

Key guard: import active rows by explicit scope/status, not by raw file length. In V54 the useful live candidates may be scoped as `ACTIVE_ENTRY`, `POST_ENTRY_MONITOR`, or similar, not only `ACTIVE_CANDIDATE`.

## Manual pick API shape
Manual picks should write to the same monitor store, not to engine output files. Minimal API fields:

```text
/api/monitor/manual?symbol=600519.SH&entry=100&sl=95&tp1=115&note=...
```

A manual row should be categorized as `手工` and still include explicit plan values (`entry_price`, `sl_price`, `tp1_price`) so TP/SL review can compare execution against the initial design.

## TP/SL review loop
When live price checks detect TP/SL:

1. Mark monitor row `CLOSED`.
2. Record `close_reason`, `exit_price`, `closed_at`, `pnl_pct`.
3. Append a review object to `closed_reviews.json`.
4. Diagnose whether the close matched the original design:
   - `SL_HIT`: classify likely signal error, entry error, stop-design error, or market-state failure.
   - `TP_HIT`: check whether TP1/runner plan was satisfied and whether a new SMC setup should become a separate re-entry.
5. Generate a concrete repair proposal, but do not mutate the engine blindly from a single live event; queue the proposal for batch audit/backtest.

## Current V53/V54 TP/SL semantics to preserve
The V53/V54 exit model is not a simple fixed TP/SL exit:

- SL is structural first, but may be capped by max risk.
- TP1/TP2 are small partial exits.
- Main size runs with structure/trend runner logic.
- Backtest first simulates the trade bar-by-bar using the planned SL/TP/trailing rules, then applies quality gates/rejection labels. Do not describe it as pre-filtering winners before computing TP/SL.

This distinction matters when explaining metrics and when auditing low RR: rejected candidates should remain available for diagnosis instead of being silently removed.

## Frontend sync checklist
When adding monitor workflow, verify all of these endpoints/pages after restart:

- `/monitor`
- `/api/monitor/state`
- `/api/monitor/ingest-daily`
- `/api/monitor/manual?...`
- `/api/live-prices` includes monitor update side effect
- `/api/summary`

Also remove any test manual picks from `positions.json` after API smoke tests.
