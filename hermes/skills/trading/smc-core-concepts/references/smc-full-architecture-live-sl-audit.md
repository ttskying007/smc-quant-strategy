# SMC Full Architecture / Live SL Root-Cause Audit Pattern

Session date: 2026-06-13

## Trigger

Use when Lei asks for a full audit of a Smart Money / SMC strategy across signal, combinations, retrace entry, entry price/location, exits, TP/SL, analysis, replay, live SLs, or low RR.

## Mandatory posture

Do not begin by widening stops, changing RR, or judging the strategy from aggregate WR. First prove whether live samples, backtest rows, frontend rows, and daily automation are the same production version and same execution contract.

## Durable findings from V86/V87 audit

### 1. Live SLs must be split into clean vs polluted samples

Before blaming the current strategy, audit:

- `positions.json`: `status`, `sample_class`, `source`, `entry_zone_relation`, `production_gate.reasons`
- `closed_reviews.json`: `reason`, `root_cause`, `sample_class`, `pnl_pct`
- `trade_ledger.json`: BUY/SELL balance and SELL reasons
- `ops_latest.json`: which selector actually generated daily picks

A high live SL count is not valid evidence against the active strategy if most closed reviews are `DIAGNOSTIC_ONLY`, `HISTORICAL_POLLUTION`, manual imports, stale picks, or generated by an older daily selector.

### 2. Check daily selector version against frontend production version

In this session, frontend default was V86, but daily automation still ran V66:

```text
smc_unified.py ACTIVE_VERSION = V86
ops_latest.json selector.cmd = /root/.hermes/scripts/v25/v66_engine.py
```

This is a P0 contract break: live SLs from the monitor cannot be attributed to V86/V87 until daily ingestion uses the same production engine.

### 3. Risk contract mismatch is a hard P0 defect

Compare production gate and monitor execution gate. A durable failure pattern:

```python
# V86 production gate
1.0 < risk_pct <= 1.5

# monitor execution gate
if risk_pct < 2.5:
    WATCH_ONLY / TOO_TIGHT_RISK
```

If research production rows require tight risk but live execution rejects tight risk, the system is not deployable. Fix the contract before further strategy tuning.

### 4. V86 signal layer can be strong while execution contract is incomplete

V86 daily-level production rows showed strong historical metrics, but all rows lacked the explicit execution contract:

- `sl`, `tp1`, `tp2`, `tp3`, `rr`, `rr_realized`, `exit_legs`
- `weekly_state`, `daily_state`, `m60_state`, `mtf_score`
- `mfe_pct`, `mae_pct`, `mfe_r`, `mae_r`, `problem_tag`

If these are missing, do not claim the production system has solved TP/SL/RR or replay closure. It only solved part of the signal gate.

### 5. Loss bucket pattern

For V85/V86, losses concentrated in:

| bucket | meaning |
|---|---|
| `EARLY_POI_CLOSE_BREAK_WITHIN_3BARS` | entry confirmation too weak or POI died quickly |
| `RECOVERY_POI_CLOSE_BREAK` | RECOVERY state is over-permissive |
| `RECOVERY_TREND_DAMAGE_WEAK_ENV` | environment quality insufficient |
| `TREND_DAMAGE_AFTER_ENTRY` | semantic stop should exit faster or gate earlier |

Use these buckets before adjusting stops.

### 6. Low RR diagnosis

Low RR is often an entry/target efficiency issue, not a win-rate issue. In V86, many low-RR trades won but harvested tiny targets. Required diagnostics:

- derived RR from `entry_price`, `risk_pct`, `liquidity_target`
- `RR<1`, `RR<1.5` counts
- entry distance from `zone_high` and smart-money cost
- MFE/MAE in percent and R
- TP-mode matrix: fixed RR vs nearest liquidity vs runner

### 7. Future-target semantic risk

If `liquidity_target` is computed using future bars after the event, it may be acceptable for exploratory replay but not for production target definition. Production target must come from entry-known levels:

- prior BSL / prior swing high
- EQH pool
- pre-entry range high
- higher-timeframe visible liquidity

### 8. Recommended repair order

Do not continue filtering small signal samples until the production contract is fixed.

P0:

1. Make daily automation use the active production engine.
2. Physically isolate or exclude `DIAGNOSTIC_ONLY` and stale/manual samples from live SL statistics.
3. Unify research gate risk bounds with monitor execution gate risk bounds.
4. Emit explicit `sl/tp1/tp2/tp3/rr/exit_legs` from production JSON.
5. Make monitor consume the same execution contract rather than deriving `sl = entry * (1-risk_pct)` and ad-hoc TP.

P1:

1. Downgrade or MTF-confirm RECOVERY rows.
2. Add early POI-death gate/replay: reject or exit fast if POI close-break happens within 3 bars.
3. Add TP1/TP2/runner legs and MFE capture reporting.
4. Replace future liquidity target with entry-known BSL.
5. Validate `zone_limit + hybrid_tight + liq_then_2r_runner` and `zone_limit + hybrid_tight + micro_0_8_1_5_3` as V88 candidates.
