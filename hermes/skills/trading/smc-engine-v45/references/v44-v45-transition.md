# V44 → V45 架构过渡: 系统教训

## 背景

V44在V43(WR=91.8%, RR=9.54x)基础上投入了大量工程努力: 5级质量分级(S/A/B/C/D)、回踩形态检测(pinbar/engulf/touch)、V14 OB重构、差异化trailing。全量4800结果: WR=79.9%, RR=3.97x, 236,556笔交易 — 比V43更差。

V45完全放弃V44的复杂架构, 回到V43的简洁模式: 4信号+POI激活+3-profile trailing。结果: WR=96.2%, RR=8.94x, PF=383。

## 核心教训

### 1. Signal Proliferation (信号泛滥) 是毒性最大的错误

```
V44: 14种信号全入场 → 236,556笔(6x V43)
V45: 仅4种信号入场   → 48,835笔
V43: 仅FVG/OB入场    → 38,810笔
```

每加一种新信号类型, 都会产生一批边缘交易。这些边缘交易的WR和RR通常低于核心信号, 稀释全局指标。14种信号中真正赚钱的只有FVG(52.5%)+OB(45.3%), 其他10种合计贡献<3%。

**规则**: 新信号必须通过独立回测验证(WR>85%, RR>7x)才能加入入口。

### 2. 质量分级越简单越好

```
V44: S/A/B/C/D 5级 + 4种profile = 20种组合
V45: binary过滤(过/不过) + 3-profile(V38.4) = 6种组合
V43: binary过滤 + 3-profile = 6种组合
```

V44的quality grade系统在A股日线1-bar约束下几乎无意义: 所有交易在1根K线内退出, 差异化trailing没有发挥作用的时间窗口。复杂的质量分级增加了优化空间但不能在实战中变现。

**规则**: 在日均持有<2bar的市场, 不要做超过binary的质量过滤。精细化参数只在多bar持有场景有效。

### 3. 回踩入场 ≠ POI激活

```
V44回踩: 检测pinbar/engulf/touch形态 → 32.9%交易, WR低于直接入场
V45 POI: 价格回到信号区域即激活 → 99.1%交易, WR=96.2%
```

回踩入场的正确方式不是"检测反转形态再去交易", 而是"价格回到信号区域意味着该信号可用"。FVG/OB本身就是机构和smart money的建仓区, 价格回到该区域就是入场信号, 不需要额外的K线形态确认。

**规则**: 信号本身定义了入场区域, 不再需要额外的形态确认层。如果有形态确认, 它应该是加分项而非必选项。

### 4. 死代码是架构毒瘤

V44的`detect_ob_v14` (277-548行, ~270行) 定义了完整的OB重构(趋势上下文+质量评分+突破验证), 但从未被`backtest_stock_v44`调用。该函数通过`detect_all_signals_v11`调用的仍然是`signals_v11.py`中的`detect_ob_v11`。

这不是bug — 这是架构设计缺陷。V14 OB在V44引擎中定义但不在信号链中注册。

**规则**: 新组件定义后必须立即集成到主流程中, 或删除。定义但不集成的代码会成为:
- 后续开发者的认知负担("这个函数是做什么的, 为什么不用?")
- 死代码维护成本
- 未来重构时的迷魂阵

### 5. Bear方向需要独立优化, 不能共用bull参数

```
V45 full(含bear): WR=90.4%, RR=7.67x, Bear P&L=-2.41%/笔
V45 bull-only:     WR=96.2%, RR=8.94x
```

Bear交易虽占总交易24.4%, 但每笔亏损2.41%。同样的trailing参数、SL策略、TP策略在bull方向WR=93.4%, 在bear方向WR=81.1%。参数不对称。

**规则**: Bear方向必须独立调参(更紧的BE, 更激进的trailing, 更高的共振门槛), 不能复用bull参数。最佳实践: Bear-only做独立回测, 确认WR>85% RR>5x后再合并。

### 6. 复杂架构 vs 简洁架构的工程代价

| 维度 | V44 (复杂) | V45 (简洁) |
|------|-----------|-----------|
| 代码行 | 1,527 | 892 |
| 扫描时间 | 1,032s | 296s |
| Bug数量 | 5个(全量扫描后才发现) | 1个(报告NoneType) |
| 参数组合 | 20种 | 6种 |
| 信号类型 | 14种 | 4种 |
| 开发周期 | 整个会话 | ~3小时 |

复杂架构不仅在结果上更差, 开发和调试成本也显著更高。V44的bug(win/loss硬编码True、Bear TP因子错误、dataclass下标访问)都是在全量扫描后才暴露的, 让早起数小时的扫描失效。

**规则**: 先跑通最小可行版本, 再逐层增加复杂度。每加一层复杂度, 先验证ROI。
